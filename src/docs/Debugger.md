# Debugger

## Overview

This is an **AST-Based Auto-Instrumentation Debugger**. This tool uses structural code analysis to inject debugging logic directly into your script, enabling time-travel debugging and deep state inspection.

* **Step & Continue:** "Step" moves forward exactly one logical instruction; "Continue" (either "Continue and Log" or "Continue Without Logging") runs until the next breakpoint.
* **Watch Expressions:** Monitor specific variables or expressions.
* **Breakpoints:** Halt execution at specific lines.
* **Conditional Breakpoints:** Halt execution when a specific condition is met.
* **Rewind & Forward (Time-Travel):** Navigate through the execution history.

## How to Use

### Setting Breakpoints in the Editor

Clicking an empty space in the **gutter** (the vertical margin to the left of the line numbers) will place a breakpoint. Clicking an existing breakpoint will remove it.

* **Solid Red Dot:** An active breakpoint is indicated by a solid red dot. This signifies that the debugger will pause execution immediately before this line is executed.
* A comment is automatically added to the code. This is how the IDE tracks the breakpoint location.
* For multi-line code blocks, such as multi-line list comprehensions, you should add the breakpoint to the **first** line.

### Configuration Page

This is the landing page when debugger tool is started.

1. **Target Files:** Select the specific files you want to track.
    * Only instrumented files support debug features. Heavy instrumentation can impact performance.
2. **Watch Expressions:** Define variables or Python expressions you want to track across the entire execution (global) or specific files.
    * Values will be visible during the debugging session.
3. **Conditional Breakpoints:** Define logic strings; the debugger will halt when **any** of the strings evaluate to `True`.
    * You can also add these condition logic strings to your watch expressions.

**Hamburger Menu:**

* **Refresh File List:** Updates the selection list of Python files. Use this if you performed file operations and the list is outdated.
* **Clean Debug Files:** Cleans up all files generated by auto-instrumentation.

### Debugger Page

The interface will jump to the **Debugger Page** once debugging starts. The debugger head will stop before the first step once the session is initiated.

**Stop/Restart** (First button in the toolbar):
* **Stop:** Sends a `[Ctrl-C]` signal to the microcontroller to terminate debugging.
    * You can still perform "time-traveling" after the session is stopped.
* **Restart:** Restarts the debugging session from the beginning.

**Debug Control** (Blue buttons in the toolbar):
* **Step:** Advances to the next logical operation.
* **Continue and Log:** Runs until a breakpoint or the end of the script.
    * All history is logged, allowing you to rewind to any step in between.
    * Code efficiency is significantly affected due to state logging.
* **Continue Without Logging:** Runs until a breakpoint or the end of the script.
    * History is **not** logged; you cannot rewind to steps in between.
    * Code efficiency is close to native with minimal impact from conditional breakpoints.

**Time-Travel** (Purple buttons in the toolbar):
* **Rewind to Beginning:** Moves to the start of the execution history.
* **Rewind:** Moves one step backward in the execution history.
* **Forward:** Moves one step forward in the execution history.
* **Forward to Latest:** Jumps instantly to the most recent real-time state.

**Meters** (Bottom status bar):
* **Time Since Last Pause:** The duration between two pauses.
    * This provides a relatively accurate track of execution time with minimum overhead.
    * Accuracy decreases if conditional breakpoints are set, as the time will include condition evaluation.
    * If continue without logging, then this will be the time between multiple steps.
* **Free Memory:** Available RAM at the current pause.
    * This will be lower than a regular run, as the debugger consumes extra RAM.
    * If RAM is too low, consider reducing the number of watch expressions and conditional breakpoints.

**Hamburger Menu:**

* **Re-instrumentation:** If file operations were performed outside the IDE, use this to re-instrument the code and restart debugging.

## Notes & Troubleshooting

> **Note:** Auto-instrumentation generates extra debugging files with names starting with `ide_debug_`. You can ignore these files or remove them after your debugging session.

### Limitations

* Debugger isn't supported if the IDE is downloaded as a html file and running locally.
    - alternative is that you can download the [whole project](https://github.com/urfdvw/circuitpython-online-ide-2/archive/refs/heads/main.zip) and host a local server in folder `/docs/`.
* Currently, only **root-level** Python files (files directly under the `CIRCUITPY` drive) are supported.
* The debugger consumes additional memory (both Flash and RAM). If you encounter memory issues, consider debugging fewer files or simplifying your watch expressions.
* The debugger does not support **SAMD21 (M0)** chips due to the lack of the `json` module in CircuitPython for these chips. These chips are also very memory-constrained and are not recommended in general.
